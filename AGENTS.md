# agent-harness

PyInstaller-frozen Python MCP server, shipped as a self-contained binary (`bin/harness-linux` on Linux, `bin/harness.exe` on Windows, both reached through the committed `bin/harness` dispatcher every launch point actually names). End users need no Python toolchain.

## Contracts an agent won't infer from the tree

- **Release is orphan-branch + dual marketplace dispatch.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) stamps the version, matrix-builds per OS, then force-pushes an orphan `release` branch holding only install-ready files and POSTs a `plugin-release` dispatch to both `seretos-agents/modular-software-factory` (curated, mode: pr — opens a review PR) and `seretos-agents/modular-software-factory-staging` (mode: direct — commits straight to main). The upsert logic itself lives once, shared by both, in `seretos-agents/modular-software-factory-dev`'s `.github/actions/update-registry`. `main` and `release` share no history — never merge between them. Clients install at the tag `agent-harness--vX.Y.Z`.
- **Version is pipeline-owned.** The `version` in `pyproject.toml` and both manifests is a placeholder; the workflow input is the source of truth and the stamp never lands on `main`. Don't hand-bump it.
- **Two host manifests, one of them points at a root `.mcp.json`.** `.claude-plugin/plugin.json` keeps its inline `mcpServers` block, resolving `command` via `${CLAUDE_PLUGIN_ROOT}`. `.codex-plugin/plugin.json` instead declares `"mcpServers": "./.mcp.json"` and the actual server lives in the root `.mcp.json` (`{"mcpServers": {"harness": {"command": "./bin/harness", "args": [], "cwd": "."}}}`) — Codex fails to load the MCP server when the same extensionless command is declared inline in its own manifest, so that form can't be reshaped, only moved out to a separate file. `release.yml`'s "Build merged staging tree" step must stage `.mcp.json` alongside `.codex-plugin` (hard copy, not `[ -f ] && … || true` — a missing file there breaks the reference, not just an optional nicety). Keep the two hosts' server name and `args` in sync by hand; nothing enforces it across files.
- **Required secret:** `ECOSYSTEM_TOKEN` — an org-wide secret (visible to every `seretos-agents` repo, no per-repo setup needed) with `Contents: RW` on both `seretos-agents/modular-software-factory` and `seretos-agents/modular-software-factory-staging`. Both `release.yml`'s two dispatch steps and `dispatch.yml` (the manual recovery workflow) fire `repository_dispatch` under it; the PR-open (curated) / direct-commit (staging) step also runs receiver-side under this same token.
- **`assets/icon.png` is a release artifact, not just a repo file.** The dispatch payload sends a `raw.githubusercontent.com/${repo}/${TAG}/assets/icon.png` URL to the marketplace, so the file must live on the orphan `release` branch at the tagged commit — `release.yml` copies `stamped/assets/` into the staging tree for exactly that reason. Ship `assets/icon.png` from day one or the marketplace listing has no image.
- **No timeout in this plugin ever cancels a run — that is a design choice, not an oversight.** `harness_wait_run`'s `timeout_seconds` and `harness wait --timeout` end only the waiting; the run is left RUNNING and only `harness_stop_run` produces CANCELLED. Making an expired wait cancel would throw away work a caller already paid for, so it is a contract break rather than a cleanup. The wait semantics and the exit-code table (0 COMPLETED, 1 FAILED, 2 limit elapsed/still RUNNING, 3 CANCELLED, 4 error) are stated in four places that have to change together: `wait_run.py`'s epilog, `harness_wait_run`'s docstring in `server.py`, `README.md`, and `skills/harness-wait/SKILL.md`.
- **`description.md` is a release artifact, not just a repo file.** The dispatch payload sends a `raw.githubusercontent.com/${repo}/${TAG}/description.md` URL in the `description_url` field, so the file must live on the orphan `release` branch at the tagged commit — `release.yml` copies it into the staging tree alongside `assets/`. Fill in its Key Features before cutting v0.0.1.
- **`bin/harness` is a committed dispatcher, not build output — the only member of `bin/` that is.** Every launch point (both `hooks/hooks.json` commands, both MCP manifests) names the same extensionless `bin/harness`. Native Windows spawners (Node/libuv for Claude Code's MCP launch, Rust's `std::process` for Codex) never run that literal file — they append `.com`/`.exe` and land on `bin/harness.exe` directly. Only a POSIX shell (Linux always; Git Bash/MSYS on Windows, which is how Claude Code runs hooks) executes `bin/harness` itself, so it is a tiny `/bin/sh` script that `exec`s `harness.exe` under MINGW/MSYS/CYGWIN or `harness-linux` otherwise. It must stay committed at mode 100755 (`git add --chmod=+x bin/harness` — `core.filemode` is commonly `false` on a Windows dev checkout, so a plain `git add` there silently drops the exec bit) and LF-only (`.gitattributes`' blanket `eol=lf` covers it since it carries no extension). `.gitignore` ignores everything else under `bin/` (`/bin/*`) but carries an explicit `!/bin/harness` negation so this one file ships from a bare dev checkout, not just from `release.yml`'s staging copy.

## OS targets

Default is multi-OS (`[windows, linux]`) and the shipped wiring already does it — you do nothing. Flip to **Windows-only** only for a genuinely Win32-bound plugin (COM / `pyvda` / `pywin32` / `comtypes`). To flip: drop `ubuntu-22.04` from the `build` matrix in `release.yml` and from `matrix.os` in `test.yml`; drop the `bin/harness-linux` assertion, its `chmod`, and its `git add`/`update-index --chmod=+x` calls in `release.yml`'s assembly + push steps, drop `bin/harness-linux` from the zip step's `EXECS` set, and drop the `bin/harness` dispatcher's Linux branch (the `*) exec "$d/harness-linux"` case in `bin/harness` — with no Linux binary ever built, that branch is dead code); and append `.exe` to `command` in `.claude-plugin/plugin.json` **only** — leave `.mcp.json`'s `command` extensionless (Codex resolves the platform binary itself; appending `.exe` there would break the Linux row).

## Gotchas (the "why" behind the code)

- **`build.ps1` runs under Windows PowerShell 5.1, PS7, and Linux `pwsh`.** It derives `$IsWindows` from `$env:OS` (5.1 lacks the auto variable) and sets no global `$ErrorActionPreference='Stop'` (PyInstaller floods stderr, which 5.1 wraps as ErrorRecords and would trip a global Stop). The smoke step gates the build on a real MCP `initialize` handshake.
- **Native bindings need `collect_all(...)` in `harness.spec`** — PyInstaller misses their lazily-generated submodules otherwise. Needing them usually also means you want `OS_TARGETS=[windows]`.
